## Scope

- Freeze the rollup contract in **both** languages at once — `contracts/go`
  and a new `contracts/rust` crate — against one shared fixture in
  `contracts/fixtures/`, so the two cannot drift without a CI failure.
- Gateway B2: one in-memory collector keyed on chi's `RoutePattern`, never the
  raw path, carrying HTTP buckets, per-backend NATS round-trip buckets and
  Redis cache hit/miss counters; flushed on a ticker and once more on graceful
  shutdown, published on `myunivokai.events.telemetry.http.v1` **through
  JetStream**.
- Build `services/telemetry-service` in Rust: a durable JetStream consumer, a
  `TelemetrySink` trait with `sinks::postgres` and `sinks::otlp` behind one
  `TELEMETRY_SINK` switch, and the `myunivokai.queries.telemetry.*` responders.
- Join the existing wake mechanism with no special case: `wake.ServiceTelemetry`
  plus `TELEMETRY_SERVICE_URL`, both already guarded by
  `internal/config/wake_config_test.go`.
- Relay two admin routes (`/api/admin/telemetry/overview`, `/routes`) and
  render them in the admin app behind a new **Telemetry** nav entry.
- Deploy: `render.yaml` block, a CI job, the local NATS ACL block and
  `.env.example` entries.

## Decisions taken inside this sprint

The plan left three questions open. Two of them block phase 3 and phase 7 and
are answered here rather than deferred; the third genuinely is not urgent.

1. **`TELEMETRY_SINK` defaults to `postgres`.** Two reasons, and the second is
   the load-bearing one. The plan's own §4 says the postgres sink exists so
   this repo's admin app can show request volume "without an external vendor
   in the loop" — a default of `otlp` would ship a Telemetry screen that has
   nothing to render. And the shipped default of every other switch in this
   repo (`AI_PROVIDER=mock`, `SERVICE_WAKE_PLATFORM=none`) reaches nobody
   else's infrastructure until an operator opts in; `otlp` pushes data to a
   third party, so it cannot be the default without breaking that rule.
2. **Retention stays at the sketched 90 days**, as `TELEMETRY_RETENTION_DAYS`
   rather than a constant, deleted by a ticker inside the service. 90 days of
   one row per minute per route bucket is small, and the number is the one
   thing an operator is most likely to want to change without a deploy.
3. **The admin navigation restructure is not decided and not built** — it is
   `DEFERRED-S5-NAV-001` below, exactly as the plan asks: revisit once the
   Telemetry screen ships and the sidebar demonstrably feels crowded.

## Deviations from the plan, stated rather than hidden

Both are inside phase 3/phase 7's own "Phase 7 picks one before
`Dockerfile.prod` is written" latitude, and both are recorded in
`services/telemetry-service/README.md` as well:

- **No `.sqlx/` offline cache; `sqlx`'s runtime query API is used instead of
  the `query!` macros.** The plan's phase 3 requires committing a `.sqlx/`
  cache generated by `cargo sqlx prepare` against a live database. That cache
  has to be regenerated on every SQL edit by whoever makes it, and a stale one
  fails the Render build rather than a test. Using `sqlx::query_as` instead
  keeps `cargo build` hermetic with no `DATABASE_URL` and no generated file to
  keep in step. The cost is real and is the reason this is written down: SQL
  mistakes surface when a query runs, not when it compiles. `sqlx::migrate!`
  is still used — it reads the migrations directory at compile time and needs
  no database.
- **`histogram` is stored as `BIGINT[]`, not `JSONB`.** The one operation that
  column exists for is being added to another histogram. Postgres adds two
  arrays elementwise inside `ON CONFLICT` with no helper function, no
  read-modify-write and no lost update under concurrent writers; JSONB would
  have needed all three. The width is still fixed at 8 by the contract and a
  `CHECK` enforces it on the row.
- **The runtime image is `debian:bookworm-slim`, not Alpine.** The plan names
  this as one of its two acceptable answers. Targeting
  `x86_64-unknown-linux-musl` to match the Go services' Alpine runtime means a
  cross-linker in the builder stage and musl builds of every transitive C
  dependency, on the repository's first Rust deploy. The extra ~25 MB of image
  is irrelevant on Render; a build that fails only in CI is not.

## Known accepted risk

**The retention trap, inherited unchanged.** `MYUNIVOKAI_EVENTS` retains 7
days. If nobody opens the Telemetry screen for eight days, the oldest rollup
envelopes expire unconsumed and that window is gone silently. This is the same
trade already accepted for `analytics-service`
([platform-evolution-research.md §Track A](../../../evolution/platform-evolution-research.md)),
and the plan's §Durability and wake explains why the usual first mitigation —
waking the read model from the write path — is deliberately *not* applied
here: a proactive wake on a 60-second flush cadence would keep the service
awake permanently and defeat scale-to-zero entirely.

## Out of scope

- The admin navigation restructure — `DEFERRED-S5-NAV-001`.
- A `sinks::fanout` writing to both sinks at once. The trait does not forbid
  it; nothing in this sprint builds it.
- Per-request wake correlation (`SERVICE_WAKING` → success as an exact causal
  trace). The approximation over `error_code_rollups` ships; the exact version
  is a schema change nobody has asked for yet.
